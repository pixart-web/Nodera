### Phase A.1 — Per-site acceptance

For every customer WordPress site, record and validate:

- DNS and canonical domain;
- HTTPS/certificate;
- homepage and representative internal pages;
- admin login path (without recording credentials);
- WordPress/PHP version;
- active plugins/themes;
- uploads/media volume;
- database size and consistency;
- forms/email delivery;
- cron/background tasks;
- external integrations;
- redirects and SEO-critical URLs;
- restart/recovery;
- backup/restore evidence.

No DNS cutover or destructive migration is to be performed without an explicit change window.

### Phase A.2 — Standardize WordPress isolation

Maintain one isolated runtime boundary per site:

- dedicated WordPress container;
- dedicated database/container or database boundary;
- dedicated volumes;
- dedicated secrets;
- dedicated Traefik route;
- no direct public database ports;
- resource limits and health checks;
- per-site backup/restore unit.

### Phase B — Infrastructure operations

After portfolio acceptance:

1. implement central monitoring and alerting;
2. configure off-host encrypted backups;
3. test isolated restore for control plane and representative WordPress site;
4. establish backup retention and per-project backup inventory;
5. perform controlled full-host reboot/recovery;
6. finalize firewall/operator checks;
7. produce the GREEN Production Gate evidence.

### Phase C — Release engineering

- publish NODERA/SERVON source changes to GitHub;
- make CI green on the current Go 1.27 toolchain;
- publish immutable application images;
- deploy from release artifacts rather than ad-hoc local tags;
- retain rollback procedure and release manifest.

### Phase D — Re-enable product development

Only after the infrastructure portfolio is stable:

1. resume Web Content Flow;
2. resume CyberAudit;
3. integrate both with NODERA operationally;
4. continue SERVON commercial packaging separately from the internal control-plane implementation.

- PHP versions: Pixart 8.1.34; Casa das Fardas, MotoGreen, BabyMoura, DiversCape and Sistema Elite DP 8.3.35.
- No host listeners were found on 3306, 5432 or 6379; database/Redis services are not directly exposed on host ports.
- WordPress volume sizes currently range from about 121 MB to 930 MB; MariaDB data directories are about 163–286 MB for the five inspected WordPress databases.
- `searchenvil.pixart.pt` is the current SearchAnvil route spelling used by the deployed configuration and returns HTTP 200 when resolved directly to the server.
- `portal.webcontentflow.com` returns HTTP 200 when resolved directly to the server.
- `cyberaudit.pixart.pt` and `kiko.pixart.pt` reach their application routers and return their expected HTTP 307 application redirects.
- `solgarvefurniture.pixart.pt` returns HTTP 200.

These are validation observations, not a claim that every site has completed final customer-domain cutover.

## Execution status — 2026-10-17

- Portfolio runtime checks are substantially complete for the six WordPress installations.
- Control-plane validation is substantially complete and remains YELLOW until off-site DR, release publication, controlled host reboot, and operator-level firewall verification are completed.
- Off-site DR cannot be activated from the current host because the Storage Box destination, pinned host key, SFTP key, and DR age recipient are not provisioned. No credentials are being fabricated or copied into source control.
- Email alerting is not implemented; external alert routing must be selected/configured before the production gate can truthfully pass.
- No destructive DNS cutover or full-host reboot is being performed while unrelated customer workloads share this node.

## Explicit non-goals for this cycle

- no new feature expansion in Web Content Flow or CyberAudit;
- no commercial website build as part of the infrastructure certification cycle;
- no fake/demo customer data used to claim operational readiness;
- no unverified `GREEN` declaration;
- no destructive DNS or production changes without a controlled change window.
