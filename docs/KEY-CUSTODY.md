# Key and secret custody

Backups of Nodera's database are useless without the key that decrypts the secrets inside them, and worthless as protection if that key sits
next to them. The rule for everything below:

> **A backup and the key that unlocks it must never live in the same place, and the only copy of a key must never live on the server it protects.**

No production key is committed to Git, and none is generated by CI or shown in docs. `scripts/init-secrets.sh` creates them on the host with
`openssl`; the values never leave that machine except through the operator custody steps below.

## Inventory

| Secret | Purpose | Format | Runtime location | Persisted | Loss means | Rotation | Recovery |
|---|---|---|---|---|---|---|---|
| **`secrets-encryption-key`** (`NODERA_SECRETS_ENCRYPTION_KEY`) | AES-256-GCM key for every value in Nodera's secret store (project database passwords, DNS/provider tokens, certificate private keys, webhook secrets) | base64 of 32 random bytes (`openssl rand -base64 32`) | `/etc/nodera/secrets/secrets-encryption-key` → read-only file in the API container only | file on host (+ **offline custody copy**) | **Permanent, unrecoverable loss of every stored secret.** Backups of the database stay readable but the secrets inside them cannot be decrypted. GCM fails closed (never garbage). | **Not supported by any tool.** A manual, deliberate re-encryption of every row is possible but not scripted (`docs/SECURITY.md` "Key rotation"). Treat the key as permanent. | Restore the file from custody before starting the restored API. |
| **`agent-signing-key`** (`NODERA_AGENT_SIGNING_KEY`) | Ed25519 seed that signs every command sent to Node Agents; its public half is pinned by each agent at enrolment | base64 of 32 random bytes | file → API container only | file on host (+ **offline custody copy**) | The control plane can no longer command existing agents. No data loss. | Replace the file, restart the API, then **revoke and re-enrol every agent** (new tokens). Queued commands are discarded. | Restore from custody (agents keep working), or accept re-enrolment. |
| `db-owner-password` / `db-app-password` | PostgreSQL roles `nodera_owner` (migrations) and `nodera_app` (API) | 40 URL-safe chars | files (+ derived `database-url`, `migrate-database-url`) | host | Only an inconvenience: reset with `scripts/db/01-roles.sql`. | **Supported:** edit the files, re-run `01-roles.sql` (idempotent, `ALTER ROLE … PASSWORD`), regenerate the URL files, restart. | Re-run `01-roles.sql` with new values. |
| `postgres-superuser-password` | PostgreSQL superuser | 40 chars | file → postgres container only | host | Reset via `docker exec … psql` over the local socket (trust). | Change in Postgres, then the file. | Not needed for recovery. |
| `redis-password` / `redis-url` | Redis auth (internal network only) | 40 chars | files → redis, api | host | Nothing durable lives in Redis. | Edit both files, restart redis + api. | Regenerate. |
| `backup-sftp-key` (+ pinned host key) | Private key for the **customer-workload** off-site backups on the Storage Box | OpenSSH private key (ed25519), **no passphrase** (non-interactive) | file → API container only | host (+ custody copy of the *public* half is on the Storage Box) | Off-site uploads stop; existing archives are untouched. | Generate a new key pair, add the public key on the Storage Box, replace the file, restart the API. | Generate a new key pair. |
| `mariadb-root-password` | Root of the **existing** MariaDB the agent manages through `docker exec` | whatever MariaDB has | file → agent container only | host; owned by whoever runs MariaDB | Agent cannot manage databases. | Rotate in MariaDB, then the file, restart the agent. | From the MariaDB owner's records. |
| **age identity** (private key for the **control-plane** backups) | Decrypts the packages made by `scripts/backup-nodera.sh` | `AGE-SECRET-KEY-1…` (`age-keygen`) | **NOT on the server.** Operator custody only. | offline (password manager + sealed second copy) | The control-plane backups become unreadable. | Generate a new pair, update `NODERA_DR_AGE_RECIPIENT` (public key) on the host; old packages need the old identity — keep it while any old package is still within retention. | n/a — this *is* the recovery key. |
| `NODERA_DR` SFTP key + pinned `known_hosts` | Upload of control-plane backup packages | OpenSSH key | `/etc/nodera/dr/` (root, 0600) | host | Control-plane backups stop uploading. | New key pair, add to the Storage Box. | Generate anew. |
| `NODERA_ANTHROPIC_API_KEY`, `NODERA_OPENAI_API_KEY` (optional) | AI providers | vendor tokens | `*_FILE` or env | host | AI features unavailable. | Rotate at the vendor. | Vendor console. |
| Session tokens, CSRF tokens, agent enrolment tokens | per-user / per-enrolment | random, stored **hashed** (sessions, tokens) | database | database | Users sign in again. | n/a | n/a |

## Generate (on the host, once)

```bash
sudo scripts/init-secrets.sh            # creates every file above; never overwrites; prints names, not values
```

For the age keypair, on **your own machine** (not the server):

```bash
age-keygen -o nodera-dr-identity.txt    # the PUBLIC key is printed; put it in /etc/nodera/backup.env as NODERA_DR_AGE_RECIPIENT
```

## Operator custody procedure (do this before any customer workload exists)

1. Copy `secrets-encryption-key` and `agent-signing-key` off the host: `sudo cat /etc/nodera/secrets/secrets-encryption-key` into a password manager
   entry **and** a second sealed medium kept elsewhere (two people / two places). Same for `nodera-dr-identity.txt`.
2. Never put these in the Storage Box, in the repository, in chat, in a ticket, or in the control-plane backup package
   (`backup-nodera.sh` deliberately does not include them — verify with `restore-nodera.sh verify` and look at the package listing).
3. Record, in the same custody entry, *which Nodera version/host* they belong to and the date.
4. **Prove it** during staging: rebuild a scratch host from nothing using only the custody copies + the latest off-site package
   (`docs/DISASTER-TESTS.md`, test 20). Until that has been done once, the custody procedure is untested.
5. Re-check custody after any rotation and every quarter (can both people still open the entry?).

## What a full recovery needs

| Needed | Comes from |
|---|---|
| Control-plane database | latest off-site `nodera-dr-*.tar.age` + the **age identity** (custody) |
| `secrets-encryption-key` | custody |
| `agent-signing-key` | custody (or re-enrol agents) |
| Non-secret config (`nodera.env`, compose file) | inside the package (`config/`) |
| Other secret files | regenerate with `init-secrets.sh` (DB/Redis passwords are re-applied by `restore-nodera.sh` through `01-roles.sql`), re-add the Storage Box key and MariaDB root password from their owners |
| Customer sites and databases | the off-site backups in the Storage Box, restored by Nodera itself once the control plane is back |
| Docker, Traefik, MariaDB, host hardening | the staging runbook (these are not Nodera's) |

## Do not

* Do not store a key in `nodera.env`, an env var, a compose file, a label, or the UI.
* Do not email, paste or screenshot key material; do not put it in ticket systems.
* Do not reuse these keys across staging and production.
* Do not "improve" security by rotating `secrets-encryption-key` on a schedule — without a re-encryption tool that destroys the data.
